Isn't six services too many for this?

By a strict scaling-forces test, yes. Users, Questions and Matching would merge: they share a request shape, a failure domain and a deploy cadence, and an earlier draft did exactly that.

They're kept separate for independent deployability and one clear owner per capability. If cold-start latency on the match path starts dominating, they recombine cheaply, because they already share a database instance. That makes it a code move rather than a data migration.

Why does a token bucket need a script at all?

A fixed-window counter needs only INCR, which is already atomic. A token bucket reads two values, computes a refill from elapsed time, and writes both back. That is multi-step, so atomicity has to come from wrapping it in a script Redis runs start to finish with nothing interleaved.

Note what the bug does not require: no threads, no shared memory. Two ordinary processes on two machines are enough. That is also why an in-process mutex is not a fix. It would guard one instance's own memory, at an address the other instance cannot reach. Atomicity has to live where the single copy of the state lives.

Why not Envoy?

Its jwt_authn filter would replace token verification cleanly, but its local rate-limit filter is per-instance, which is exactly the split-bucket bug. Its global one delegates to a separate gRPC service backed by Redis. Envoy relocates this problem rather than removing it. Kong is the honest comparison, and it's what I'd reach for commercially.

Why not just pin both users to one instance?

Cloud Run's session affinity is best-effort, and it pins a client, not a group. The two people in a session are different clients connecting at different moments, so nothing would co-locate them in the first place, and affinity evaporates on scale-down. Fanning through Redis makes instance placement irrelevant, which is the property that survives autoscaling.

Why snapshot every 30 seconds rather than on every edit?

Per-keystroke writes would exhaust the free Postgres tier and add latency to the hot path. 30 seconds bounds worst-case loss, and the disconnect and SIGTERM snapshots mean the routine cases, a deploy or a closed tab, lose nothing at all. Only an ungraceful crash hits the full window.

Decisions worth defending

4 of the 9 ADRs

An ADR is reserved for decisions where the rejected option was genuinely defensible and the tradeoff is still being paid.

ADR-04 Firebase Auth instead of self-hosted auth

The first draft built auth directly: bcrypt, RS256 signing, opaque refresh tokens rotated in Redis. The decision was to buy it. Identity is security-critical and fully solved, and Google's credential-stuffing detection and signing-key rotation are not things a solo project reproduces.

An unplanned benefit worth naming: bcrypt was the only CPU-bound work anywhere on a request path, and Node runs all application JavaScript on one thread. Roughly 250 ms of hashing would have stalled every other request on that instance. Buying auth deleted that hazard, and it's part of why 80 concurrent requests per instance is a safe number.

Deliberately kept: the Gateway verifies tokens itself against a JWKS rather than delegating to an SDK, so the property that mattered survives the switch. The edge can verify, but it cannot mint.

Accepted: vendor lock-in on identity, a revoked token stays valid for up to an hour, and local dev depends on the Auth emulator.
ADR-08 A custom gateway instead of Kong

Kong DB-less provides all four things this Gateway does, the rate limiter included. Build it anyway: the token bucket is the one component whose concurrency bug a product would fix on my behalf, and the fix only means something if you've seen the broken version fail.

Note the symmetry with ADR-04. Same test, opposite answer. Auth was bought because it is risk without insight. The gateway was built because the insight is what's inside it.

Accepted: no circuit breaking, retries or mTLS. A hand-written proxy is a single point of failure I now own.
ADR-09 One Postgres instance, one schema and one role per service

Each service reaches its own schema through its own Postgres role, so a cross-service read is rejected by the database, not discouraged by convention. That is asserted by a test, not left as a rule people remember. No foreign key crosses a schema boundary.

Database-per-service is the textbook answer and was rejected: session creation touches profiles, questions and sessions, and across separate databases no transaction covers them. That needs a saga, which is a lot of machinery for a two-person editor, and it wants an always-on orchestrator the cost ceiling forbids.

Accepted: one instance is a shared failure domain. The microservices claim rests on services owning their tables, not their instances.
ADR-07 A replayable event log, not a queue

A queue deletes on consume, so a bug in the summary logic means the data needed to recompute is gone. A log keeps entries after reading, so the fix is rewinding the bookmark.

The async split is also what creates the at-least-once problem that forces idempotency, keyed by user, by session, and by entry id. That is what converts at-least-once into effectively exactly-once, and it's the reason this phase is worth building.

Accepted: Redis Streams in production, because no free managed Kafka exists and an always-on broker breaks the cost ceiling.

Try the pizza query. Nothing in the index is about pizza, so every chunk scores below the floor and the system refuses instead of inventing an answer.

The scoring function
score(q, d) = Σt ∈ q IDF(t) · ( tf · (k₁ + 1) ) / ( tf + k₁ · (1 − b + b · |d| / avgdl) ) IDF(t) = ln( 1 + (N − df + 0.5) / (df + 0.5) ) k₁ = 1.2, b = 0.75

The k₁ term saturates, so the tenth occurrence of a word says far less than the second. The b term normalises by length, so a long chunk doesn't win just by containing more words. Those two corrections are most of why BM25 beats naive TF-IDF.

Why not just paste the notes into an LLM?

A whole semester of notes doesn't fit a context window, and re-sending everything per question is slow and expensive. The right architecture is a persistent index with retrieval: fetch the few relevant chunks, then answer from those with citations.

Where the concurrency lives

The index is read-only after build, so reads are lock-free by design. The parts that need synchronisation are the rate limiter and the hot-query cache, and later a scatter-gather coordinator fanning a query across shards with goroutines and merging results back.

Build order

from PLAN.md
  • Ingest, in Python, once. Walk the notes folder, chunk at 300 to 500 words with overlap, tag each chunk with subject and page, fetch embeddings through a worker pool.
  • Index, BM25 and top-k in Go. Tokenise, stem, drop stop-words, build the inverted index, select top-k with a min-heap.
  • Hybrid retrieval. Embed the query, brute-force cosine top-k, fuse with BM25. Verified by a meaning-level query that surfaces synonym chunks BM25 alone misses.
  • Cited answers, and refusals. Refuse when the top retrieval score is below threshold. An off-topic question must get a refusal, not an answer.
  • Eval harness. 15 to 20 question and expected-answer pairs measuring hit-rate and refusal correctness, with every failure logged in FAILURES.md.
  • Then scale. Shard the index with a scatter-gather coordinator, add a concurrency-safe LRU for hot queries, and compress postings.

Why the floor is plain code, not the model

The verdict is tripwire-BLOCK OR judge-BLOCK. Reading a planted honeytoken, connecting out to a non-registry host, or spawning a shell during an install is never acceptable, and any one blocks on its own, decided before a model is consulted. The model handles the gray areas on top of that floor, and by construction it can only make the gate stricter, never weaker.

Why the gray zone needs a judge at all

The same log line means opposite things for different packages. Reading .env is an attack for a typosquat, but it is python-dotenv's entire legitimate job. A plain rule over the raw log would either miss real attacks or block half of PyPI, so ambiguous cases go to the judge, told to block when unsure. A false block costs a retry. A false pass costs the machine.

What Airlock does not address

It addresses malicious code that runs: install-time trojans, credential stealers, typosquats. It does not address accidental source-code leaks, and doesn't claim to. Its blind spots are named in the design doc rather than left for a judge to find.
