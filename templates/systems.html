Isn't six services too many for this?

Probably, yes. Users, Questions and Matching could be one service. They handle similar requests, fail in similar ways, and ship on the same cadence. An earlier draft had them merged.

I split them so each one can be deployed on its own and has a single clear owner. If cold starts on the match path ever become the bottleneck, merging them back is cheap: they already share a database, so it's a code move, not a data migration.

Why does this need a script at all?

A simple counter only needs INCR, which Redis already does in one step. A token bucket reads two values, works out a refill from the time elapsed, then writes both back. That is three steps, and anything can happen between them unless Redis runs the whole thing start to finish.

Notice what this bug does not need: no threads, no shared memory. Two ordinary processes on two machines are enough. A lock inside one process cannot fix it either, since it only guards that machine's own memory. The fix has to live where the single copy of the data lives.

Why not Envoy?

Envoy handles token checking well. But its local rate limiter counts per machine, which is exactly the bug above, and its global one just hands the job to another service backed by Redis. It moves the problem rather than solving it. Kong is the fair comparison, and it's what I'd actually deploy.

Why not just put both people on the same server?

Cloud Run can try to keep one visitor on one machine, but not a pair. The two people join at different moments as different clients, so nothing would put them together in the first place, and the stickiness disappears when it scales down. Routing through Redis makes it stop mattering which machine anyone lands on.

Why save every 30 seconds instead of every keystroke?

Saving on every keystroke would burn through the free database tier and slow down typing. Thirty seconds caps the worst case, and since it also saves when someone disconnects or the server shuts down, the everyday cases lose nothing at all. Only a hard crash costs you the full window.

Decisions I would defend in an interview

4 of the 9 ADRs

I only write one of these when the option I turned down was genuinely a good one, and I'm still living with the cost of choosing otherwise.

ADR-04 Firebase Auth instead of self-hosted auth

The first draft built auth directly: bcrypt, RS256 signing, opaque refresh tokens rotated in Redis. The decision was to buy it. Identity is security-critical and fully solved, and Google's credential-stuffing detection and signing-key rotation are not things a solo project reproduces.

An unplanned benefit worth naming: bcrypt was the only CPU-bound work anywhere on a request path, and Node runs all application JavaScript on one thread. Roughly 250 ms of hashing would have stalled every other request on that instance. Buying auth deleted that hazard, and it's part of why 80 concurrent requests per instance is a safe number.

Deliberately kept: the Gateway verifies tokens itself against a JWKS rather than delegating to an SDK, so the property that mattered survives the switch. The edge can verify, but it cannot mint.

Accepted: vendor lock-in on identity, a revoked token stays valid for up to an hour, and local dev depends on the Auth emulator.
ADR-08 A custom gateway instead of Kong

Kong DB-less provides all four things this Gateway does, the rate limiter included. Build it anyway: the token bucket is the one component whose concurrency bug a product would fix on my behalf, and the fix only means something if you've seen the broken version fail.

Note the symmetry with ADR-04. Same test, opposite answer. Auth was bought because it is risk without insight. The gateway was built because the insight is what's inside it.

Accepted: no circuit breaking, retries or mTLS. A hand-written proxy is a single point of failure I now own.
ADR-09 One Postgres instance, one schema and one role per service

Each service reaches its own schema through its own Postgres role, so a cross-service read is rejected by the database, not discouraged by convention. That is asserted by a test, not left as a rule people remember. No foreign key crosses a schema boundary.

Database-per-service is the textbook answer and was rejected: session creation touches profiles, questions and sessions, and across separate databases no transaction covers them. That needs a saga, which is a lot of machinery for a two-person editor, and it wants an always-on orchestrator the cost ceiling forbids.

Accepted: one instance is a shared failure domain. The microservices claim rests on services owning their tables, not their instances.
ADR-07 A replayable event log, not a queue

A queue deletes on consume, so a bug in the summary logic means the data needed to recompute is gone. A log keeps entries after reading, so the fix is rewinding the bookmark.

The async split is also what creates the at-least-once problem that forces idempotency, keyed by user, by session, and by entry id. That is what converts at-least-once into effectively exactly-once, and it's the reason this phase is worth building.

Accepted: Redis Streams in production, because no free managed Kafka exists and an always-on broker breaks the cost ceiling.

Try the pizza one. Nothing in the index is about pizza, so everything scores too low and it refuses rather than making something up.

The scoring function
score(q, d) = Σt ∈ q IDF(t) · ( tf · (k₁ + 1) ) / ( tf + k₁ · (1 − b + b · |d| / avgdl) ) IDF(t) = ln( 1 + (N − df + 0.5) / (df + 0.5) ) k₁ = 1.2, b = 0.75

k₁ makes repetition count for less each time, so the tenth mention of a word matters far less than the second. b adjusts for length, so a long chunk can't win just by containing more words. Those two corrections are most of why BM25 beats simpler scoring.

Why not just paste the notes into an LLM?

A semester of notes doesn't fit, and re-sending all of it for every question is slow and expensive. Build the index once, pull the few chunks that matter, then answer from those and cite them.

Where the concurrency lives

Nothing writes to the index after it's built, so reads need no locks at all. The parts that do need care are the rate limiter and the cache, and later the piece that fans a query out across shards and merges the results back.

What I am building, in order

from PLAN.md
  • Ingest, in Python, once. Walk the notes folder, chunk at 300 to 500 words with overlap, tag each chunk with subject and page, fetch embeddings through a worker pool.
  • Index, BM25 and top-k in Go. Tokenise, stem, drop stop-words, build the inverted index, select top-k with a min-heap.
  • Hybrid retrieval. Embed the query, brute-force cosine top-k, fuse with BM25. Verified by a meaning-level query that surfaces synonym chunks BM25 alone misses.
  • Cited answers, and refusals. Refuse when the top retrieval score is below threshold. An off-topic question must get a refusal, not an answer.
  • Eval harness. 15 to 20 question and expected-answer pairs measuring hit-rate and refusal correctness, with every failure logged in FAILURES.md.
  • Then scale. Shard the index with a scatter-gather coordinator, add a concurrency-safe LRU for hot queries, and compress postings.

Why the hard rules are plain code, not AI

Some things are never acceptable during an install: reading the fake credentials we planted, calling out to an unknown server, or opening a shell. Any one of those blocks immediately, decided by ordinary code before any model is asked. The model only handles the unclear cases on top, and it can only ever make the gate stricter.

Why the unclear cases need a judge

The same behaviour means opposite things depending on the package. Reading .env is an attack for a fake package, but it is literally python-dotenv's job. A fixed rule would either miss real attacks or block half of PyPI. So unclear cases go to the judge, which is told to block when unsure. A wrong block costs a retry. A wrong pass costs you the machine.

What Airlock doesn't cover

It catches malicious code that runs: trojans that fire on install, credential stealers, and fake lookalike packages. It does not catch accidental source-code leaks, and doesn't pretend to. The blind spots are written down in the design doc.
