What the script prevents

A fixed-window counter needs only INCR, which is already atomic. A token bucket reads two values, computes a refill from elapsed time, and writes both back — that's multi-step, so atomicity has to come from wrapping it in a script Redis runs start to finish with nothing interleaved.

Note what the bug does not require: no threads, no shared memory. Two ordinary processes on two different machines are enough. Which is also why an in-process mutex is not a fix — it would guard one instance's own memory, at an address the other instance cannot reach and has never heard of. Atomicity has to live where the single copy of the state lives.

Why not Envoy

Its jwt_authn filter would replace token verification cleanly, but its local rate-limit filter is per-instance — exactly the split-bucket bug — and its global one delegates to a separate gRPC rate-limit service backed by Redis. Envoy doesn't remove this problem; it deploys another container to solve it the same way. Kong DB-less is the honest comparison, and it's what I'd reach for commercially.

The hard part: convergence across instances

a real CRDT · computed in this page

Two users in one session can land on different Collab instances, which share no memory. Type in both panes at once, drop a connection and reconnect it, or raise the latency — the two replicas still land on the same document. That's the property a CRDT buys, and it's why the merge can't be hand-rolled: a subtly wrong merge only shows itself under concurrent edits.

Why not sticky sessions

The obvious fix is pinning both users to one instance. It doesn't work: Cloud Run's session affinity is best-effort and pins a client, not a group. The two people in a session are different clients connecting at different moments, so nothing would co-locate them in the first place — and affinity evaporates on scale-down. Fanning through Redis makes instance placement irrelevant, which is the property that survives autoscaling.

Why snapshot every 30s

Per-keystroke writes would exhaust the free Postgres tier and add latency to the hot path. 30 seconds bounds worst-case loss, and the disconnect and SIGTERM snapshots mean the routine cases — a deploy, a scale-down, a closed tab — lose nothing at all. Only an ungraceful crash hits the full window.

Decisions worth defending

4 of the 9 ADRs

An ADR here is reserved for decisions where the rejected option was genuinely defensible and the tradeoff is still being paid. An obvious choice gets a one-line note instead.

ADR-04 Firebase Auth instead of self-hosted auth

The first draft built auth directly — bcrypt, RS256 signing, opaque refresh tokens rotated in Redis. The decision was to buy it. Identity is security-critical and fully solved, and Google's credential-stuffing detection, leaked-password checks and signing-key rotation are not things a solo project reproduces.

An unplanned benefit worth naming: bcrypt was the only CPU-bound work anywhere on a request path, and Node runs all application JavaScript on one thread — so ~250 ms of hashing would have stalled every other request on that instance. Buying auth deleted that hazard, and it's part of why 80 concurrent requests per instance is a safe number rather than an optimistic one.

Deliberately kept: the Gateway verifies tokens itself against a JWKS rather than delegating to an SDK, so the property that mattered — the edge can verify but cannot mint — survives the switch.

Accepted: vendor lock-in on identity; a revoked token stays valid for up to an hour; local dev and CI depend on the Auth emulator.
ADR-08 A custom gateway instead of Kong

Kong DB-less provides all four things this Gateway does — JWT verification, routing, CORS and distributed rate limiting, the limiter included via its Redis policy. Build it anyway: the token bucket is the one component whose concurrency bug a product would fix on my behalf, and the fix is only meaningful if you've seen the broken version fail.

Note the symmetry with ADR-04 — same test, opposite answer: auth bought because it is risk without insight, the gateway built because the insight is what's inside it.

Accepted: no circuit breaking, retries or mTLS; a hand-written proxy is a single point of failure I now own; every WebSocket burns a slot on the Gateway as well as on Collab.
ADR-09 One Postgres instance, one schema and one role per service

Each service reaches its own schema through its own Postgres role, so a cross-service read is rejected by the database, not discouraged by convention — and that's asserted by a test, not left as a rule people remember. No foreign key crosses a schema boundary; a session row stores firebase_uid and question_id as plain columns, validated by API call at creation time.

Database-per-service is the textbook answer and was rejected: session creation touches profiles, questions and sessions, and across separate databases no transaction covers them. That needs a saga — compensating actions, persisted saga state, a sweeper for crashed runs — which is a lot of machinery for a two-person editor, and wants an always-on orchestrator the cost ceiling forbids.

Accepted: one instance is a shared failure domain and a shared connection budget; the "microservices" claim rests on services owning their tables, not their instances.
ADR-07 A replayable event log, not a queue

A queue deletes on consume, so a bug in the summary logic means the data needed to recompute is gone. A log keeps entries after reading, so the fix is rewinding the bookmark — or adding a consumer later and still seeing history.

The async split is also what creates the at-least-once problem that forces idempotency: queue-join keyed by user, session-end by session, event consumption by entry id. That's what converts "at-least-once" into "effectively exactly-once", and it's the reason this phase is worth building at all.

Accepted: Redis Streams in production because no free managed Kafka exists and an always-on broker breaks the cost ceiling. Kafka lives in docker-compose only, behind a three-method interface.

Recall

Designed

A search engine over a semester of my own notes that answers questions with cited sources — and refuses when retrieval confidence is low. Hand-rolled inverted index, BM25 ranking and hybrid retrieval in Go. No search library, because the index is the point.

The search box below is real BM25, computed in your browser over a nine-chunk sample corpus: the IDF values, term contributions and rankings are genuinely calculated, not precomputed. It exists so the retrieval path is legible. Recall itself will do this in Go over my actual notes.

Why not just paste the notes into an LLM?

A whole semester of notes doesn't fit a context window, and re-sending everything per question is slow and expensive. The right architecture is a persistent index with retrieval: fetch the few relevant chunks, then let the model answer from those with citations.

Where the concurrency lives

The index is read-only after build, so reads are lock-free by design. The parts that actually need synchronisation are the rate limiter and the hot-query cache — and later, a scatter-gather coordinator fanning a query across shards with goroutines and merging the results back.

Try the last example. Nothing in the index is about pizza, so every chunk scores below the floor and the system refuses instead of inventing an answer — the behaviour the citation requirement exists to enforce. The + expansion toggle is an illustration of what hybrid retrieval buys, using a small hand-written map; the real system fuses BM25 with cosine similarity over embeddings, which is a different and better thing.

score(q, d) = Σt ∈ q IDF(t) · ( tf(t,d) · (k₁ + 1) ) / ( tf(t,d) + k₁ · (1 − b + b · |d| / avgdl) ) IDF(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) ) k₁ = 1.2, b = 0.75

The k₁ term saturates: the tenth occurrence of a word says far less than the second. The b term normalises by length, so a long chunk doesn't win just by containing more words. Those two corrections are most of why BM25 beats naive TF-IDF.

Build order

from PLAN.md
  • Ingest (Python, once) — walk the notes folder, parse, clean, chunk at 300–500 words with overlap, tag each chunk with subject/file/page, fetch embeddings through a worker pool, write one data file.
  • Index + BM25 + top-k (Go) — tokenise, lowercase, stem, drop stop-words; build the inverted index; score with BM25; select top-k with a min-heap.
  • Hybrid retrieval — embed the query, brute-force cosine top-k, fuse with BM25. Verified by a meaning-level query that surfaces synonym chunks BM25 alone misses.
  • Cited answers, and refusals — retrieve, build the prompt, cite sources, and refuse when the top retrieval score is below threshold. An off-topic question must get a refusal, not an answer.
  • Eval harness — 15–20 question/expected pairs measuring retrieval hit-rate, answer quality and refusal correctness, with every failure case logged in FAILURES.md.
  • Then scale — shard the index across processes with a scatter-gather coordinator (goroutine fan-out, channel fan-in, k-way merge), a concurrency-safe LRU for hot queries, and postings compression.

Airlock

A safety gate that sits between an AI coding agent and every package it tries to install. Each install is detonated in a disposable sandbox before it touches the machine, then read statically, matched against known malware and reputation-scored, with a model issuing the final verdict.

Why the floor is plain code

The final verdict is tripwire-BLOCK OR judge-BLOCK. Reading a planted honeytoken, connecting out to a non-registry host, or spawning a shell during an install is never acceptable, and any one of those blocks on its own — decided by an if-statement, before a model is consulted. The model handles the gray areas on top of that floor, and by construction it can only make the gate stricter, never weaker.

Why the gray zone needs a judge

The same log line means opposite things for different packages: reading .env is an attack for a typosquat but is python-dotenv's entire legitimate job. A plain rule over the raw log would either miss real attacks or block half of PyPI — so ambiguous cases go to the judge, told to block when unsure, because a false block costs a retry and a false pass costs the machine.

Honest scope: Airlock addresses malicious code that runs — install-time trojans, credential stealers, typosquats. It does not address accidental source-code leaks, and doesn't claim to. Its blind spots are named in the design doc rather than left for a judge to find.
